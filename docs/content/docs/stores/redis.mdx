title: Redis Store
description: Redis store for high-throughput, low-latency deployments.

The Redis store uses [Grove KV](https://github.com/xraph/grove) with the `redisdriver` for key-value storage. It stores entities as JSON blobs and uses Redis sorted sets and sets for indexing and querying.

## Usage

### Standalone

```go
import (
    "github.com/xraph/grove/kv"
    _ "github.com/xraph/grove/kv/drivers/redisdriver"
    redisstore "github.com/xraph/relay/store/redis"
)

store, err := kv.Open("redis", "redis://localhost:6379/0")
if err != nil {
    log.Fatal(err)
}

s := redisstore.New(store)

r, err := relay.New(relay.WithStore(s))
```

### With Forge extension

When using the Forge extension with Grove KV, the store is resolved from the DI container:

```go
app.Use(extension.New(
    extension.WithGroveKV(""),  // uses the default grove kv.Store
))
```

Or via YAML config:

```yaml
extensions:
  relay:
    grove_kv: ""
```

## Data model

Entities are stored as JSON blobs under prefixed keys. Indexes use Redis sorted sets (scored by timestamp) and sets for efficient lookup.

### Key prefixes

| Prefix | Purpose |
|--------|---------|
| `relay:evtype:<id>` | Event type entity |
| `relay:ep:<id>` | Endpoint entity |
| `relay:evt:<id>` | Event entity |
| `relay:del:<id>` | Delivery entity |
| `relay:dlq:<id>` | DLQ entry entity |

### Index keys

| Key pattern | Type | Purpose |
|-------------|------|---------|
| `relay:z:evtype:all` | Sorted set | All event types by creation time |
| `relay:z:ep:tenant:<tid>` | Sorted set | Endpoints per tenant |
| `relay:z:ep:all` | Sorted set | Every endpoint across tenants, for an every-tenant listing |
| `relay:z:evt:all` | Sorted set | All events by creation time |
| `relay:z:evt:tenant:<tid>` | Sorted set | Events per tenant |
| `relay:z:del:pending` | Sorted set | Pending deliveries by `next_attempt_at` |
| `relay:z:del:ep:<eid>` | Sorted set | Deliveries per endpoint |
| `relay:z:dlq:all` | Sorted set | All DLQ entries by failure time |
| `relay:s:evtype:active` | Set | Active (non-deprecated) event type IDs |
| `relay:s:ep:tenant:<tid>:enabled` | Set | Enabled endpoint IDs per tenant |

### Unique constraints

| Key pattern | Purpose |
|-------------|---------|
| `relay:u:evtype:name:<name>` | Event type name uniqueness |
| `relay:u:evt:idem:<key>` | Idempotency key uniqueness |

## Migrations

Redis has no schema, but `Migrate()` still has work to do: it builds the
`relay:z:ep:all` index that lists endpoints across every tenant.

Older versions only indexed endpoints per tenant, so after an upgrade the global
index is empty until `Migrate()` fills it from the per-tenant indexes. Relay's
extension runs `Migrate()` at startup unless you set `DisableMigrate`. If you
disable it, or build the store yourself, call `Migrate()` once before you rely on
an every-tenant listing.

Until it has run, listing endpoints with an empty tenant returns
`ErrEndpointIndexNotBuilt` rather than an empty list. An empty list would read as
"no endpoints", which is how an audit of unsigned endpoints could report clean.
Listing a named tenant works either way.

Two marker keys track it:

| Key | Expires | Purpose |
|-----|---------|---------|
| `relay:migrated:ep_all:built` | Never | The index has been built and can be trusted |
| `relay:migrated:ep_all:v1` | 24 hours | The backfill ran recently, so boots skip it |

The second one expires on purpose. If you roll back to a version that did not
maintain the global index, endpoints created during the rollback are missing
from it until the backfill runs again, which happens within a day of
redeploying. To repair it straight away, delete `relay:migrated:ep_all:v1` and
restart, or call `Migrate()`.

## Namespaced kv stores

Pass `redisstore.New` a kv store with a namespace hook if you want two relays on
one redis, each with its own data:

```go
kvStore, _ := kv.Open(rdb, kv.WithHook(middleware.NewNamespace("app1")))
store := redisstore.New(kvStore)
```

The store sends commands two ways. Records go through kv, so the hook moves
them under the prefix. Every sorted-set and set index, the idempotency keys, the
replay claim (a WATCH/MULTI transaction), the delivery queue (a Lua script), the
migration markers and the wake channel go through the raw go-redis client, which
no hook ever sees. So the store resolves each of those keys itself, by running
the kv store's hooks over the key the way grove does for the matching kv command,
and sends the result to redis. Record ids are the only thing stored inside an
index, and the Lua script builds no keys of its own, so the keys passed in are the
only ones there are.

What that gets you:

- two namespaces can use the same tenant ids, idempotency keys and event type
  names without seeing each other's rows;
- lists, indexes, gets and deletes see their own namespace only, and a delete
  removes the record under its namespaced key;
- replay and the claim work per namespace, and `Purge` only removes its own
  entries;
- `Dequeue` claims from its own queue, and the wake channel only wakes the
  relays in the same namespace;
- `Migrate` builds each namespace's global indexes from that namespace's own
  per-tenant indexes, and its markers are namespaced too. A new namespace needs
  its own `Migrate` call, and an every-tenant list returns
  `ErrEndpointIndexNotBuilt` until then.

You need grove v1.7.0 or later. Earlier versions ignored the hook on deletes,
multi-key reads and every collection command, so a namespaced store left deleted
records in place. Relay's redis store uses `kv.ErrHookKeyCount`, which arrived in
v1.7.0, so it won't compile against an older grove.

### What `Migrate` refuses

A namespace has to apply to every command, and has to be a prefix. `Migrate`
resolves a probe key under every command the store uses (get, set, delete,
exists, scan, the sorted-set and set commands, and eval) and returns
`ErrKVKeysInconsistent` if they don't all give the same key, or if the result
isn't the probe with something put in front of it.

That refuses a namespace scoped to reads only, one scoped to writes only, one that
skips a single command such as scan, and a hook that appends to keys instead of
prefixing them. For the first three there is no right answer to give: kv would
write a record at one name and read it from another, so every read after a write
misses. The last can't be undone by a scan, and the migration scans to find
indexes. Because the check runs locally, it writes nothing to redis when it
refuses.

`ErrKVRewritesKeys` is the old name for the same error. It's deprecated, still
matches, and a store that namespaces every key no longer returns it.

The check then confirms that the key the store computes is the key kv really uses.
It writes a probe through kv and deletes it at the computed key, then writes one at
the computed key and reads it through kv. That guards against grove changing how it
hands keys to hooks, which the store mirrors because grove doesn't export it. A
failure here returns the same error.

This second step refuses only on proof. A failed refusal stops the app booting, so
a probe that simply goes missing, which is what replication lag or eviction looks
like behind a proxy that reads from replicas, is not treated as proof and passes.
It can miss a disagreement in that situation, but it won't refuse a store that
works. The probes carry a one-minute TTL, so they clean up even when nothing can
delete them.

Other hooks are not refused. In grove kv v1.7.0 the encrypt and compress hooks
still don't change what gets stored: records, endpoint secrets included, are
written in plain text whether or not you add them.

Hooks that run before every command see the store's raw commands too, but only
their pre-query half. A hook that denies a command makes the matching raw
command fail with `kv.ErrHookDenied`, and nothing in a pipeline is sent if one
of its keys is denied. Logging and metrics hooks see one call per key resolved,
not one per redis command.

If you set `DisableMigrate`, this check does not run.

## Internals

| Aspect | Detail |
|--------|--------|
| Driver | Grove KV with `redisdriver` (go-redis v9) |
| Migrations | Builds the global endpoint index; see above |
| Dequeue | Sorted set range + atomic key update |
| Transactions | Redis single-key atomicity |
| JSON fields | All entities stored as JSON blobs |
| Pagination | Client-side offset/limit on sorted set results |
| Ping | `kv.Ping(ctx)` |
| Close | Closes the KV store |

## When to use

- High-throughput, low-latency delivery pipelines.
- When Redis is already part of your infrastructure.
- Ephemeral or cache-friendly workloads where Redis persistence (RDB/AOF) is acceptable.
- Workloads that benefit from Redis clustering for horizontal scaling.

## Limitations

- No multi-key transactions -- operations are atomic per key only.
- Pagination is applied client-side after fetching sorted set members.
- Data durability depends on Redis persistence configuration (RDB, AOF, or none).
