title: Redis Store
description: Redis store for high-throughput, low-latency deployments.

The Redis store uses [Grove KV](https://github.com/xraph/grove) with the `redisdriver` for key-value storage. It stores entities as JSON blobs and uses Redis sorted sets and sets for indexing and querying.

## Usage

### Standalone

```go
import (
    "github.com/xraph/grove/kv"
    _ "github.com/xraph/grove/kv/drivers/redisdriver"
    redisstore "github.com/xraph/relay/store/redis"
)

store, err := kv.Open("redis", "redis://localhost:6379/0")
if err != nil {
    log.Fatal(err)
}

s := redisstore.New(store)

r, err := relay.New(relay.WithStore(s))
```

### With Forge extension

When using the Forge extension with Grove KV, the store is resolved from the DI container:

```go
app.Use(extension.New(
    extension.WithGroveKV(""),  // uses the default grove kv.Store
))
```

Or via YAML config:

```yaml
extensions:
  relay:
    grove_kv: ""
```

## Data model

Entities are stored as JSON blobs under prefixed keys. Indexes use Redis sorted sets (scored by timestamp) and sets for efficient lookup.

### Key prefixes

| Prefix | Purpose |
|--------|---------|
| `relay:evtype:<id>` | Event type entity |
| `relay:ep:<id>` | Endpoint entity |
| `relay:evt:<id>` | Event entity |
| `relay:del:<id>` | Delivery entity |
| `relay:dlq:<id>` | DLQ entry entity |

### Index keys

| Key pattern | Type | Purpose |
|-------------|------|---------|
| `relay:z:evtype:all` | Sorted set | All event types by creation time |
| `relay:z:ep:tenant:<tid>` | Sorted set | Endpoints per tenant |
| `relay:z:ep:all` | Sorted set | Every endpoint across tenants, for an every-tenant listing |
| `relay:z:evt:all` | Sorted set | All events by creation time |
| `relay:z:evt:tenant:<tid>` | Sorted set | Events per tenant |
| `relay:z:del:pending` | Sorted set | Pending deliveries by `next_attempt_at` |
| `relay:z:del:ep:<eid>` | Sorted set | Deliveries per endpoint |
| `relay:z:dlq:all` | Sorted set | All DLQ entries by failure time |
| `relay:s:evtype:active` | Set | Active (non-deprecated) event type IDs |
| `relay:s:ep:tenant:<tid>:enabled` | Set | Enabled endpoint IDs per tenant |

### Unique constraints

| Key pattern | Purpose |
|-------------|---------|
| `relay:u:evtype:name:<name>` | Event type name uniqueness |
| `relay:u:evt:idem:<key>` | Idempotency key uniqueness |

## Migrations

Redis has no schema, but `Migrate()` still has work to do: it builds the
`relay:z:ep:all` index that lists endpoints across every tenant.

Older versions only indexed endpoints per tenant, so after an upgrade the global
index is empty until `Migrate()` fills it from the per-tenant indexes. Relay's
extension runs `Migrate()` at startup unless you set `DisableMigrate`. If you
disable it, or build the store yourself, call `Migrate()` once before you rely on
an every-tenant listing.

Until it has run, listing endpoints with an empty tenant returns
`ErrEndpointIndexNotBuilt` rather than an empty list. An empty list would read as
"no endpoints", which is how an audit of unsigned endpoints could report clean.
Listing a named tenant works either way.

Two marker keys track it:

| Key | Expires | Purpose |
|-----|---------|---------|
| `relay:migrated:ep_all:built` | Never | The index has been built and can be trusted |
| `relay:migrated:ep_all:v1` | 24 hours | The backfill ran recently, so boots skip it |

The second one expires on purpose. If you roll back to a version that did not
maintain the global index, endpoints created during the rollback are missing
from it until the backfill runs again, which happens within a day of
redeploying. To repair it straight away, delete `relay:migrated:ep_all:v1` and
restart, or call `Migrate()`.

## Key-rewriting kv hooks are not supported

Pass `redisstore.New` a kv store without a namespace hook.

The store reads and writes some keys through the raw go-redis client (every
sorted-set and set index, and the replay claim) and the rest through kv (the
records). That only works if both clients mean the same key by the same name.
A namespace hook moves the records under a prefix the raw client never sees,
and nothing errors. Instead:

- deleting an endpoint leaves its record, secret included, in redis;
- a replayed DLQ entry's record is never removed;
- replay cannot find any record, and answers "dlq entry not found";
- two relays sharing one redis still collide on every index key, so the
  namespace does not isolate them anyway.

`Migrate()` checks for this before anything else and returns
`ErrKVRewritesKeys` if it finds it. It probes both ways: a key written through
kv has to be where the raw client expects it, and a key written through the raw
client has to be readable through kv. That catches a namespace applied to reads
only, to writes only, or to both.

It refuses only on proof. A failed refusal stops the app booting, so a probe
that simply goes missing, which is what replication lag or eviction looks like
behind a proxy that reads from replicas, is not treated as proof and passes.
That makes the check best-effort. It can miss a rewrite in that situation, but
it will not refuse a store that works.

It leaves no keys behind. The probes carry a one-minute TTL, so they clean up
even in the case where nothing can delete them.

Other hooks are not refused. Note that in grove kv v1.6.3 the encrypt and
compress hooks do not change what gets stored: records, endpoint secrets
included, are written in plain text whether or not you add them.

If you set `DisableMigrate`, this check does not run.

## Internals

| Aspect | Detail |
|--------|--------|
| Driver | Grove KV with `redisdriver` (go-redis v9) |
| Migrations | Builds the global endpoint index; see above |
| Dequeue | Sorted set range + atomic key update |
| Transactions | Redis single-key atomicity |
| JSON fields | All entities stored as JSON blobs |
| Pagination | Client-side offset/limit on sorted set results |
| Ping | `kv.Ping(ctx)` |
| Close | Closes the KV store |

## When to use

- High-throughput, low-latency delivery pipelines.
- When Redis is already part of your infrastructure.
- Ephemeral or cache-friendly workloads where Redis persistence (RDB/AOF) is acceptable.
- Workloads that benefit from Redis clustering for horizontal scaling.

## Limitations

- No multi-key transactions -- operations are atomic per key only.
- Pagination is applied client-side after fetching sorted set members.
- Data durability depends on Redis persistence configuration (RDB, AOF, or none).
